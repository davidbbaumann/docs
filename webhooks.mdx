Webhooks let Nexus notify your systems the moment something happens in your workspace — a candidate is created, an application moves to a new stage, or a form is submitted. Instead of polling the Nexus API, you register an HTTPS endpoint and Nexus sends a signed `POST` request to it for every subscribed event.

<Note>
  Webhooks are currently available to pilot customers. Contact your Nexus account manager to enable delivery for your workspace.
</Note>

## How it works

<Steps>
  <Step title="Enable the Webhooks extension">
    A user with the **Extensions Manage** permission switches on Webhooks under **Settings → Extensions → Webhooks**.
  </Step>
  <Step title="Create an endpoint">
    A user with the **Webhooks Manage** permission adds an HTTPS URL, selects the events to subscribe to, and activates the endpoint.
  </Step>
  <Step title="Store the signing secret">
    Nexus shows the signing secret (`whsec_...`) **once**. Store it securely — you need it to verify every request.
  </Step>
  <Step title="Receive and verify events">
    Nexus sends a signed JSON payload to your endpoint. Verify the signature, respond with a `2xx` status, and process the event asynchronously.
  </Step>
</Steps>

## Permissions

Access is controlled by permissions that can be added to any role under **Settings → Roles**.

| Permission | Allows |
| --- | --- |
| `extensions:manage` | Switch the Webhooks extension on or off for the workspace |
| `webhooks:view` | View endpoints (without full URL or secret), the event catalog, recorded events and deliveries |
| `webhooks:manage` | Create, edit, activate, deactivate and delete endpoints; rotate secrets; send test events; replay deliveries; reactivate paused endpoints |

`webhooks:manage` includes `webhooks:view`. By default, only the **Workspace Admin** role has both.

<Warning>
  When Webhooks is switched off, all active endpoints are deactivated. Switching it back on does **not** reactivate them automatically.
</Warning>

## Event payload

Every request body uses the same envelope. Payloads are intentionally **thin**: they contain identifiers only, never names, emails or other personal data. Use the Nexus API or MCP to fetch the current state of the record.

```json
{
  "id": "evt_0285acf6-91b4-4b59-994f-4d6411f32a68",
  "event": "candidate.updated",
  "timestamp": "2026-10-26T13:55:08.866Z",
  "workspace_id": "06479da7-9b24-40b1-a7f5-1e948ca57403",
  "actor": {
    "type": "user",
    "id": "84b5a877-b4b8-49e4-9710-d647e212d85b",
    "channel": "ui"
  },
  "data": {
    "id": "3ca8c964-69fb-4e5c-940b-b95d80cb12ec",
    "entity_type": "candidate"
  }
}
```

### Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Unique event ID (`evt_...`). Identical to the `webhook-id` header. Use it for deduplication. |
| `event` | string | Event type, e.g. `candidate.created`. |
| `timestamp` | string | ISO 8601 UTC time when the event occurred. |
| `workspace_id` | string | UUID of the Nexus workspace. |
| `actor` | object | Who triggered the event. |
| `data` | object | Identifiers of the affected record(s). |

### Actor

| Field | Type | Description |
| --- | --- | --- |
| `type` | string | `user` or `system`. |
| `id` | string \| null | UUID of the user, if known. |
| `channel` | string | Where the change came from, e.g. `ui` or `system`. |

<Info>
  Channel attribution is being expanded. Today many changes are reported as `system` even when a user made them. Do not build business logic on `channel` yet.
</Info>

## Event types

| Event | Triggered when |
| --- | --- |
| `account.created` / `.updated` / `.deleted` | An account is created, changed or deleted |
| `contact.created` / `.updated` / `.deleted` | A contact is created, changed or deleted |
| `candidate.created` / `.updated` / `.deleted` | A candidate is created, changed or deleted |
| `application.created` / `.updated` / `.deleted` | An application is created, changed or deleted |
| `project.created` / `.updated` / `.deleted` | A project is created, changed or deleted |
| `job.created` / `.updated` / `.deleted` | A job is created, changed or deleted |
| `assignment.stage_changed` | A candidate moves to another stage in a project |
| `form.submitted` | A form is submitted |
| `agent_run.completed` | An AI agent run finishes |
| `webhook.test` | A manager clicks **Send test event** |

Deleted events contain only the ID of the deleted record. When a record is deleted together with related records, each related record may produce its own event.

## HTTP request

Nexus sends a `POST` request with `Content-Type: application/json` and these headers, following the [Standard Webhooks](https://www.standardwebhooks.com) specification:

| Header | Description |
| --- | --- |
| `webhook-id` | Unique event ID, same as `id` in the body |
| `webhook-timestamp` | Unix timestamp (seconds) of the send attempt |
| `webhook-signature` | One or more space-separated signatures, each `v1,<base64>` |

## Verifying signatures

The signature is an HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{raw body}`, keyed with the base64-decoded part of your secret after `whsec_`. Always verify against the **raw** request body and reject timestamps older than 5 minutes.

<CodeGroup>

```javascript Node.js
import { Webhook } from "standardwebhooks";

const wh = new Webhook(process.env.NEXUS_WEBHOOK_SECRET.replace("whsec_", ""));

app.post("/webhooks/nexus", express.raw({ type: "application/json" }), (req, res) => {
  try {
    const event = wh.verify(req.body, req.headers);
    queue.add(event);          // process asynchronously
    res.sendStatus(200);
  } catch {
    res.sendStatus(401);
  }
});
```

```python Python
from standardwebhooks.webhooks import Webhook

wh = Webhook(os.environ["NEXUS_WEBHOOK_SECRET"].removeprefix("whsec_"))

@app.post("/webhooks/nexus")
def nexus_webhook(request):
    try:
        event = wh.verify(request.body, dict(request.headers))
    except Exception:
        return Response(status=401)
    enqueue(event)
    return Response(status=200)
```

```javascript Manual (Node.js)
import crypto from "node:crypto";

function verify(rawBody, headers, secret) {
  const id = headers["webhook-id"];
  const ts = headers["webhook-timestamp"];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;

  const key = Buffer.from(secret.replace("whsec_", ""), "base64");
  const expected = crypto
    .createHmac("sha256", key)
    .update(`${id}.${ts}.${rawBody}`)
    .digest("base64");

  return headers["webhook-signature"].split(" ").some((sig) => {
    const value = sig.split(",")[1] ?? "";
    return value.length === expected.length &&
      crypto.timingSafeEqual(Buffer.from(value), Buffer.from(expected));
  });
}
```

</CodeGroup>

## Secret rotation

When you generate a new secret, the previous one stays valid for **24 hours**. During that window each request carries two signatures, so you can deploy the new secret without downtime. A manager can end the overlap early.

## Responding and retries

- Respond with a `2xx` status within **5 seconds**. Do heavy processing in a background job.
- Redirects are not followed and count as failures.
- Timeouts, network errors, unresolvable hosts, `408`, `429` and `5xx` responses are retried after **1 min, 5 min, 30 min, 2 h and 6 h** (6 attempts in total). After that the delivery is marked **dead**.
- Other `4xx` responses fail immediately without retry.
- Events can arrive more than once and out of order. Deduplicate by `webhook-id` and use `timestamp` for ordering.

## Endpoint health and alerts

| Status | Condition |
| --- | --- |
| Healthy | Deliveries succeed |
| Failing | 10 consecutive failed deliveries |
| Paused | 50 consecutive failures, or 10 failures with no success in 24 hours |

When an endpoint becomes **Failing**, every Webhooks manager in the workspace receives an email in their profile language (at most once per endpoint per 24 hours). **Paused** endpoints receive no new deliveries until a manager clicks **Reactivate**. Test events never affect endpoint health.

## Logs and replay

Under **Settings → Extensions → Webhooks** you find:

- **Event catalog** — all event types with example payloads.
- **Recorded events** — every event recorded for your workspace, with payload inspection.
- **Deliveries** — every attempt with status, response code, duration and attempts. Managers can replay finished deliveries.

## Endpoint requirements

- HTTPS on port 443 with a valid certificate.
- Publicly reachable; private, loopback and internal addresses are rejected.
- Only active endpoints receive events, and only while the Webhooks extension is on.

  <Card title="Verify every request" icon="shield-check">

  <Card title="Respond fast" icon="bolt">

  <Card title="Be idempotent" icon="repeat">
